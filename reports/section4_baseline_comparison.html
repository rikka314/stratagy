4. Baseline Comparison

This section addresses Course Requirement 4 (AIE1902): “The simple models mentioned in our lecture notes should be implemented to compare with your proposed models whenever possible.” We implement three canonical forecasting baselines—Naive (Buy-and-Hold), Mean (Moving Average), and Drift (Linear Trend Extrapolation)—drawn directly from the course lecture material. Each baseline is translated into a position-based trading rule, executed through the identical back-testing engine that runs our proposed models, and evaluated with the same suite of performance metrics. This ensures that every performance comparison is conducted on a strictly level playing field: same data splits, same execution assumptions, same cost structure (no stop-loss / take-profit for baselines), and same metric definitions.

4.1 Unified Comparison Interface – ModelResult

All baselines and all proposed models produce the same ModelResult dictionary (defined at the top of core/baselines.py, line 17): 

ModelResult = dict[str, Any]

# Canonical keys:
{
    "label":         str,            # Human-readable display name
    "equity_series": pd.Series,      # Strategy equity curve (start = 1.0)
    "returns":       pd.Series,      # Daily strategy returns
    "trades_df":     pd.DataFrame,   # Trade-by-trade detail (entry, exit, P&L)
    "metrics":       dict | None,    # Filled later by evaluation module
}

This contract is intentionally minimal yet sufficient. The equity_series and returns fields are indexed by date (parsed in _sim_to_model_result(), lines 27–40) so that all downstream charting and metric functions can align heterogeneous models on a common time axis. The metrics slot is populated lazily: baselines are first constructed with metrics=None, and the evaluation module (core/evaluation.py → compute_performance_metrics()) fills it during the comparison phase. This two-stage design decouples signal generation from performance measurement, allowing the same metric code to be applied uniformly to any ModelResult—whether it originates from a baseline, from the SM/FSM search family, or from the RSM regime-switching family.

The formal schema is also documented in document/MODEL_INTERFACES.md. The offline research framework (model-test/model_test/config.py, lines 203–205) registers every baseline as a ModelSpec with group="baseline", guaranteeing that Stage A research runs always include all three baselines alongside every proposed model variant.

4.2 Naive Baseline – Buy-and-Hold

4.2.1 Course Foundation

The Naive Forecast from the course lecture notes states:

ŷT+h = yT

That is, the best forecast for any future horizon h is simply the last observed value. In a trading context this translates to a perpetual long position: since the forecast never predicts a decline, the rational action under the naive model is to buy at the first opportunity and hold indefinitely. The naive baseline therefore represents the minimum bar that any active strategy must clear—if a model cannot beat buy-and-hold after accounting for transaction friction and timing risk, it adds no value.

4.2.2 Mathematical Formulation

Let Pt denote the closing price on day t. Define the daily simple return as:

rt = Pt / Pt−1 − 1

The naive strategy holds a constant position of 1.0 (fully invested) for the entire observation period. The strategy equity curve is the cumulative product of gross daily returns:

Equity(t) = Equity(t−1) × (1 + rt)    with  Equity(0) = 1.0

Equivalently, expanding the recursion:

Equity(T) = ∏t=1T (1 + rt) = PT / P0

This confirms that the naive equity curve is exactly proportional to the raw price series, scaled so that the initial value equals 1.

4.2.3 Implementation Detail

Entry point: core/baselines.py → naive_baseline(df) (lines 90–104).

  1. ATR computation: The helper _ensure_atr(df, atr_period=14) (line 20) adds a 14-period Average True Range column if absent. Although the naive baseline does not use ATR for stop-loss or take-profit, the back-test engine simulate_strategy() reads the atr column during its position management loop (for other strategies), so every input DataFrame must carry it.
  2. Position column: A uniform target_position = 1.0 is assigned to every row (line 96): 
    d["target_position"] = 1.0
    This instructs the back-test engine to be fully invested on every bar.
  3. Simulation call: The function invokes: 
    sim_df, trades_df = simulate_strategy(
    d,
    initial_position=1,      # start already in-position
    stop_loss_mult=0.0,      # no stop-loss
    take_profit_mult=0.0,    # no take-profit
    return_trades=True,
)
    Setting initial_position=1 means the strategy enters the market from day 0 (line 49 of core/backtest.py: in_position = True and entry_price = df["close"].iloc[0]). Combined with stop_loss_mult=0.0 and take_profit_mult=0.0, no risk-management exit is ever triggered, so the position remains at 1.0 for the entire duration. The back-test engine computes strategy_return[t] = position[t-1] × returns[t] (line 117 of backtest.py) and strategy_equity[t] = ∏(1 + strategy_return) (line 118).
  4. Result packaging: _sim_to_model_result("Naive（买入持有）", sim_df, trades_df) extracts the strategy_equity and strategy_return columns from the simulation output, wraps them in date-indexed pd.Series, and returns the canonical ModelResult dictionary.

4.2.4 Trade Profile

Because target_position is always 1.0 and the position is never closed, extract_trades() (lines 127–217 of backtest.py) identifies exactly one trade spanning the entire test period. The hold_days equals the total number of trading days, and trade_return equals the cumulative return of the period. Win-rate is trivially 100% if the stock rose and 0% if it fell. This single-trade characteristic makes the naive baseline a useful reference for turnover analysis: any proposed model with a higher Sharpe but dramatically higher turnover should be scrutinized for transaction cost sensitivity.

4.3 Mean Baseline – Moving Average

4.3.1 Course Foundation

The Mean Model from the course lectures forecasts every future value as the arithmetic mean of recent observations:

ŷT+h = (1/T) ∑t=1T yt

In a trading context, using a rolling window of length w rather than the full history yields the classical Simple Moving Average (SMA) crossover rule: when the current price exceeds its recent average, momentum is judged to be positive and a long position is warranted; otherwise, the position is flattened. This is one of the oldest and most widely studied technical trading rules, dating back to Brock, Lakonishok & LeBaron (1992).

4.3.2 Mathematical Formulation

Define the w-period rolling mean as:

SMAw(t) = (1/w) ∑i=0w−1 Pt−i

The target position rule is:

pos(t) = { 1.0  if  Pt > SMAw(t),   0.0  otherwise }

For the first w−1 bars where insufficient history exists to compute the rolling mean, the position defaults to 0.0 (the min_periods=window parameter in pandas.rolling().mean() produces NaN for those bars, which the np.where condition maps to the “otherwise” branch).

With the default w = 60 trading days (≈ 3 calendar months), the mean baseline captures medium-term trend direction. A shorter window (e.g., 20) would be more responsive but generate more whipsaw trades; a longer window (e.g., 200) would be smoother but react too slowly to regime changes. The choice of 60 is a balanced default that aligns with common institutional practice.

4.3.3 Implementation Detail

Entry point: core/baselines.py → mean_baseline(df, window=60) (lines 107–120).

The position logic is factored into a reusable helper mean_target_position(df, window=60) (lines 43–54) that is also imported by the WebApp workflow (ui/single_stock_workflow.py, line 35: from core.baselines import mean_target_position): 

def mean_target_position(df: pd.DataFrame, window: int = 60) -> pd.Series:
    close = pd.to_numeric(df["close"], errors="coerce")
    rolling_mean = close.rolling(window=window, min_periods=window).mean()
    target = np.where(close > rolling_mean, 1.0, 0.0).astype(float)
    return pd.Series(target, index=df.index, name="target_position")

Key implementation notes:

  1. pd.to_numeric(..., errors="coerce") defensively handles any non-numeric entries in the close column (a downstream safeguard inherited from the data-loading pipeline in core/data.py).
  2. min_periods=window ensures that the rolling mean is only computed when a full w-bar lookback is available, preventing warm-up bias.
  3. The comparison close > rolling_mean uses a strict inequality, meaning that when the price exactly equals the moving average, the position is flat. This avoids edge-case oscillation on perfectly sideways days.

The simulation call uses initial_position=0 (starting flat), reflecting the fact that the mean baseline must first “earn” its entry signal by waiting for price to exceed the rolling average. As with all baselines, stop_loss_mult=0.0 and take_profit_mult=0.0.

4.3.4 Trade Profile

Unlike the naive baseline, the mean baseline generates multiple trades over the test period. Each crossing of the price above/below the rolling mean triggers an entry/exit. The extract_trades() function identifies contiguous position > 0 segments and computes per-trade holding period, return, and win/loss classification.

Empirically, the 60-day mean baseline acts as a trend filter: it stays invested during sustained up-trends and exits during prolonged drawdowns. However, in choppy or mean-reverting markets, it suffers from frequent whipsaw entries—buying slightly above the average and selling slightly below—which erodes returns through short-lived losing trades.

4.4 Drift Baseline – Linear Trend Extrapolation

4.4.1 Course Foundation

The Drift Model from the course lecture notes extends the naive forecast by adding a constant rate of change estimated from the training sample:

ŷT+h = yT + h × β̂   where   β̂ = (yT − y1) / (T − 1)

This is equivalent to drawing a straight line between the first and last observations of the training period and projecting that line into the future. It captures the average historical drift (secular trend) of the price series but is entirely blind to curvature, cyclicality, or regime changes.

4.4.2 Mathematical Formulation

Let the training period span indices i = 0, 1, …, S−1 where S = split_idx is the first out-of-sample index. Define:

β̂ = (PS−1 − P0) / (S − 1)

The extrapolated prediction line at any index i is:

PredLine(i) = P0 + β̂ × i

The trading rule for the test period (i ≥ S) is:

pos(i) = { 1.0  if  Pi ≥ PredLine(i),   0.0  otherwise }

During the training period (i < S), the position is fixed at 0.0. This is a deliberate design choice: the drift parameter β̂ is estimated from training data, so generating positions on the same data would introduce in-sample bias.

Interpretation: When β̂ > 0 (up-trending training period), the prediction line slopes upward. If the actual price stays above this line in the test period, the drift model goes long; if the price falls below the line, it exits. This creates a dynamic threshold that rises over time, preventing the model from degenerating into “always long” or “always flat” based solely on the sign of β̂. When β̂ < 0 (down-trending training period), the prediction line slopes downward, meaning the model will only go long if the price rallies above the declining extrapolation—a contrarian signal.

4.4.3 Implementation Detail

Entry point: core/baselines.py → drift_baseline(df, split_idx) (lines 123–143).

The position logic is factored into drift_target_position(df, split_idx) (lines 57–87), also imported by the WebApp workflow: 

def drift_target_position(df: pd.DataFrame, split_idx: int) -> pd.Series:
    n = len(df)
    target = np.zeros(n, dtype=float)
    close = pd.to_numeric(df["close"], errors="coerce").to_numpy(dtype=float, copy=False)
    idx = np.arange(n, dtype=float)

    if split_idx >= 2:
        y_first = float(close[0])
        y_last_train = float(close[split_idx - 1])
        beta = (y_last_train - y_first) / (split_idx - 1)
        pred_line = y_first + beta * idx
        if split_idx < n:
            target[split_idx:] = np.where(
                close[split_idx:] >= pred_line[split_idx:], 1.0, 0.0
            )
    ...

Key implementation notes:

  1. Three code paths handle edge cases:
    • split_idx ≥ 2 (normal case): full drift estimation with at least two training points.
    • split_idx ≤ 0 (no explicit split): the entire series is treated as training data, and positions are generated for the full range using the end-to-end slope.
    • split_idx == 1 (single training point): β̂ is undefined (division by zero), so the function falls back to a level-comparison against the first price P0.
  2. Vectorized computation: Both pred_line and the comparison close[split_idx:] ≥ pred_line[split_idx:] are NumPy array operations, avoiding Python-level loops for performance.
  3. Training-period zero position: target = np.zeros(n) initializes all positions to 0; only the slice target[split_idx:] is overwritten, ensuring no in-sample signal leakage.

The simulation call uses initial_position=0. The back-test engine reads the target_position column and enters the market only when the first 1.0 appears in the test segment.

4.4.4 Trade Profile

The drift baseline typically generates a moderate number of trades, fewer than the mean baseline (because the prediction line is a smooth monotone curve rather than a jagged rolling average) but more than the naive baseline (which never exits). In trending markets, the drift model may remain invested for long stretches when the price stays above the extrapolation; in volatile markets, the crossings between price and prediction line generate alternating long/flat positions. The holding period per trade is generally longer than that of the mean baseline, as the drift line changes slowly (by β̂ per day) compared to the rolling mean, which can shift substantially with each new data point entering or exiting the window.

4.5 Comparison Framework – Execution Fairness

4.5.1 Shared Back-Test Engine

All three baselines are executed through the same simulate_strategy() function in core/backtest.py (lines 34–124). This is the identical engine used for every proposed model (SM, FSM, RSM and all optimized variants). The engine operates as follows:

  1. Position tracking (lines 48–113): A forward loop reads target_position[i] each bar, checks for stop-loss/take-profit exits (disabled for baselines via mult=0.0), and records the effective position[i].
  2. Return computation (lines 116–119): 
    returns = df["close"].pct_change().fillna(0)
df["strategy_return"] = df["position"].shift(1).fillna(initial_position) * returns
df["strategy_equity"] = (1 + df["strategy_return"]).cumprod()
df["buy_hold_equity"] = (1 + returns).cumprod()
    • position.shift(1) ensures that the position used on day t was determined on day t−1 (no look-ahead bias).
    • buy_hold_equity is always computed as a parallel benchmark, regardless of the strategy being simulated.

Key fairness parameters for baselines:

Parameter Value for all baselines Rationale
stop_loss_mult 0.0 Disables ATR-based stop-loss. Baselines are simple forecast models with no risk-management overlay. Comparing them against proposed models that also run without stops (or with stops, noted separately) keeps the comparison clean.
take_profit_mult 0.0 Disables ATR-based take-profit for the same reason.
initial_position 1 (Naive) / 0 (Mean, Drift) Naive is always fully invested from day 0; Mean and Drift must first satisfy their respective entry conditions.
return_trades True All baselines request trade extraction to enable per-trade analysis (win-rate, profit/loss ratio, holding period).

4.5.2 Unified Performance Evaluation

After simulation, every ModelResult is evaluated by core/evaluation.py → evaluate_strategy() (lines 146–196), which calls two sub-functions:

  1. compute_performance_metrics(equity_series, benchmark_series) (lines 14–65) computes:

  2. compute_trade_stats(trades_df, n_trading_days) (lines 68–143) computes:

The top-level build_comparison_table(results) function (lines 199–241) aggregates all evaluated models into a single pd.DataFrame with a stable, deterministic column order: label → cumret → annret → maxdd → sharpe → winrate → pnl_ratio → avg_hold → turnover → bench_* → excess_return. This table is rendered identically in both the offline research reports and the live WebApp.

4.8.1 Interpretation Guidelines

  • A proposed model should outperform all three baselines on the Sharpe ratio to be considered a meaningful improvement. The Sharpe ratio is the primary risk-adjusted metric; a model that merely achieves higher cumulative returns by taking on proportionally more risk (deeper drawdowns, higher volatility) has not demonstrated genuine alpha.
  • Excess return over the naive baseline quantifies the value of active trading. If a model’s excess return is negative, the investor would have been better off simply buying and holding.
  • Win rate and P&L ratio contextualize the nature of outperformance. A model with a low win rate but high P&L ratio achieves its edge through a few large winners (trend-following style); a model with high win rate but low P&L ratio achieves its edge through many small gains (mean-reversion style). Comparing these profiles against the baselines reveals whether the proposed model is genuinely capturing a different signal or merely a noisy variation of the baseline.
  • Consistency across rolling windows is essential. A model that beats baselines in the primary analysis window but fails in rolling robustness tests is likely overfit. The offline research framework (Section 4.6) specifically tests for this by including baselines in every rolling window.
  • Maximum drawdown comparison reveals tail risk. A model with a better Sharpe but substantially worse max drawdown than the baselines may be unsuitable for risk-averse investors, even if its expected return is higher.
Implementation Note: The complete comparison infrastructure—from baseline signal generation through back-testing to metric computation—shares every line of execution code with the proposed models. There is no separate “baseline mode” or simplified back-test path. This design eliminates any possibility that performance differences arise from differences in execution mechanics rather than differences in the underlying trading signals.
