5. Parameter Learning & WebApp Adjustability

This section addresses Requirement 5 of the AIE1902 course project: “Briefly describe how the parameters of the models are learned. Some important parameters should be adjustable in your webapp.” We provide an exhaustive treatment covering (i) the full search parameter space and its validity constraints, (ii) the composite objective function with regularization, (iii) three distinct optimization methods (Bayesian, Random Search, Genetic Algorithm), (iv) factor analysis and ML filter training, (v) adaptive regime model training, and (vi) how every key parameter is exposed to the end user through the Streamlit web application’s interactive sidebar.

5.1.2 Validity Constraints

Implementation: core/optimizer.py — function _is_valid_candidate() (lines 208–226).

Not all combinations of parameter values produce a logically coherent strategy. The optimizer enforces six structural constraints; any candidate violating one or more is immediately rejected (returns None) without running the backtest:

#ConstraintFormulaRationale
C1 Fast EMA < Slow EMA ema_fast < ema_slow Without this ordering the trend filter (fast EMA crosses above slow EMA) is semantically undefined.
C2 MACD fast < MACD slow macd_fast < macd_slow The MACD line is defined as the difference of a shorter and longer EMA; reversed periods yield a mirror signal.
C3 Entry score > Exit score entry_threshold > exit_threshold Ensures a hysteresis band between entry and exit to prevent immediate flip-flop.
C4 Short momentum < Long momentum momentum_short < momentum_long The short-term momentum window must be strictly shorter than the medium-term window to capture different time-scale signals.
C5 Mid percentile < High percentile score_mid_pct < score_high_pct The tiered position sizing requires a monotonically increasing percentile boundary.
C6 Exit signals ≤ Entry signals exit_min_signals ≤ entry_min_signals The entry gate should be at least as strict as the exit gate to avoid an asymmetry where positions are easier to open than to close.

5.2 Composite Objective Function

Implementation: core/optimizer.py — functions _score_metrics() (line 295), _evaluate_candidate_frame() (line 382), and _regularization_penalty() (line 229).

The optimization objective is a multi-component scalar score designed to balance risk-adjusted returns with out-of-sample generalization and parameter parsimony. It is constructed in three layers:

5.2.1 Per-Period Score

For any contiguous slice of the backtest (training sub-period or validation sub-period), the per-period score S is computed from the simulation metrics as: 

S = Sharpe + 2.0 × ExcessReturn − 0.5 × |MaxDrawdown| − 0.25 × Turnover

Where:

  • Sharpe: annualized Sharpe ratio of strategy returns (risk-free rate assumed zero).
  • ExcessReturn: strategy total return minus buy-and-hold total return over the same period.
  • |MaxDrawdown|: absolute value of the maximum peak-to-trough drawdown, penalizing large losses.
  • Turnover: fraction of trading days on which a new position is entered, penalizing excessive trading.

5.2.2 Train–Validation Combination

The in-sample data (up to split_idx) is further divided at sub_train_end = 0.7 × split_idx (minimum 50 rows). Sub-scores Strain and Sval are computed on [0, sub_train_end) and [sub_train_end, split_idx) respectively, and then blended with a generalization penalty: 

raw_score = 0.25 × Strain + 0.75 × Sval − 0.20 × |Strain − Sval|

The 0.75 weighting on the validation score strongly favors out-of-sample performance. The 0.20 × |ΔS| gap penalty discourages parameter combinations where training performance diverges from validation performance—a direct signal of overfitting. If the sub-training split would be too short (< 50 rows), the system falls back to a single-period score: raw_score = Strain.

5.2.3 Regularization

A parameter-distance regularization term further restrains the optimizer from selecting exotic parameter combinations far from the expert-chosen defaults: 

final_score = raw_score − λ × ∑i ((parami − defaulti) / (hii − loi))2

Where:

  • λ = 0.02 for the standard search space (SM mode) or 0.03 for the extended space (hold-until-exit / FSM mode). See SearchEvaluationCache.__init__() (line 464).
  • The sum runs over all continuous (non-boolean) parameters. Each term is the squared normalized deviation of the candidate value from its default, ensuring that the penalty is scale-invariant across parameters with different units and ranges.
  • For boolean parameters, the penalty is float(candidate ≠ default)—a unit step.

This L2-style regularization biases the search toward the neighbourhood of known-good defaults, reducing the risk of fitting to noise in short or volatile training windows.

5.3 Three Optimization Methods

Implementation: core/optimizer.py — three public entry points, all sharing the same SearchEvaluationCache and objective function. Before any optimizer runs, the three built-in strategy presets (Conservative, Balanced, Aggressive) are evaluated via evaluate_presets_for_optimization() and the best preset is used as a warm-start seed for each method.

5.3.1 Bayesian Optimization (Optuna TPE)

Entry point: bayesian_optimize_params() (line 750).
Sampler: Tree-structured Parzen Estimator (TPE) — optuna.samplers.TPESampler(seed=random_seed) (line 838).

Bayesian optimization builds a probabilistic surrogate model of the objective function and uses it to intelligently choose the next candidate to evaluate, rather than sampling blindly. The Optuna TPE sampler specifically:

  1. Partitions trials into “good” and “bad” sets based on a quantile threshold of observed scores.
  2. Fits independent kernel density estimators (KDE) to each set, yielding l(x) (good) and g(x) (bad) distributions.
  3. Maximizes the ratio l(x)/g(x) (an approximation of the Expected Improvement acquisition function) to propose the next candidate.
  4. Handles mixed types natively: suggest_int, suggest_float, and suggest_categorical (for booleans) are called per-parameter via _suggest_candidate() (line 571).

Warm-start: The best preset parameters are injected into the Optuna study as the first trial using study.enqueue_trial() (line 843), ensuring that the surrogate model starts from a known-good region of the search space.

Evaluation: Each trial calls cache.evaluate(), which runs the full pipeline (indicators → signals → backtest) and caches results by normalized parameter key, preventing redundant evaluation of duplicate candidates. The per-trial score is raw_score − regularization_penalty.

Advantages: TPE is significantly more sample-efficient than random search in high-dimensional mixed-type spaces. It concentrates evaluations in promising regions while still exploring under-sampled areas, making it the recommended default method when computation budget is limited.

5.3.2 Random Search

Entry point: random_search_params() (line 658).
Sampling: Uniform random sampling via numpy.random.Generator with a fixed seed (DEFAULT_SEARCH_RANDOM_SEED = 42).

Random search generates n_trials candidate parameter vectors independently from the uniform distribution over the valid search bounds. Each candidate is clipped to bounds via _clip_candidate_params() and checked against the six validity constraints. Invalid candidates are silently skipped (no retry logic), so the effective number of evaluated trials may be smaller than n_trials.

The first trial (index 0) uses the warm-start seed parameters directly (line 724–725), ensuring that the random search never performs worse than the best preset. All subsequent trials are purely random.

Purpose: Random search serves as a robust baseline and sanity-check comparator. In practice it provides surprisingly good coverage due to the “blessing of dimensionality”—in 33-dimensional space, random samples tend to cover corners that grid search would miss entirely. It also provides a lower bound on expected optimization performance against which Bayesian and Genetic methods are measured.

5.3.3 Genetic Algorithm (GA)

Entry point: genetic_algorithm_optimize_params() (line 861).
Defaults: population_size = 30, generations = 20, crossover_rate = 0.8, mutation_rate = 0.2.

The Genetic Algorithm implements a population-based evolutionary strategy inspired by natural selection. The GA operates as follows:

PhaseOperatorImplementation Detail
Initialization Random population + seed injection If warm-start seed_params are provided, the seed and 3 Gaussian-mutated variants are prepended to the initial population (lines 977–984). Remaining slots are filled with uniform random individuals. Up to population_size × 10 attempts are made to satisfy validity constraints.
Fitness evaluation Multi-threaded parallel evaluation Each individual is evaluated via _evaluate() using ThreadPoolExecutor(max_workers) where max_workers = min(cpu_count, population_size, 8) (line 974). This exploits GIL-releasing NumPy/pandas operations for significant speedup.
Selection Tournament selection (k=3) _tournament_select() (line 938) randomly picks 3 individuals and selects the one with the highest fitness. This applies moderate selection pressure while maintaining genetic diversity.
Crossover BLX-α blend crossover (α = 0.5) _blx_alpha_crossover() (line 947): for each continuous parameter, the child value is sampled uniformly from [min(p1, p2) − α·Δ,  max(p1, p2) + α·Δ], where Δ is the parent range. Boolean parameters are inherited from a random parent. Applied with probability crossover_rate (default 0.8).
Mutation Gaussian perturbation _gaussian_mutate() (line 927): each parameter is independently perturbed with probability mutation_rate (default 0.2). For continuous parameters: value += Normal(0, 0.1 × (hi − lo)). For booleans: the value is flipped. The mutated candidate is clipped to bounds via _clip_candidate_params().
Elitism Top-2 preservation The 2 highest-fitness individuals from each generation are copied unchanged into the next generation (line 1009–1021), guaranteeing that the best discovered solution is never lost.
Repair Constraint satisfaction retry After crossover + mutation, if the child violates validity constraints, up to 5 retries are attempted with fresh random mutation (lines 1034–1042). If all retries fail, a completely random valid individual is substituted.

Total evaluations: population_size + generations × population_size = 30 + 20 × 30 = 630 evaluations with default settings. Each evaluation is cached in the shared SearchEvaluationCache (keyed by normalized parameter tuple), so repeated encounters of the same candidate are free.

5.3.4 Shared Evaluation Cache

Implementation: core/optimizer.py — class SearchEvaluationCache (line 443).

All three optimizers share a request-scoped evaluation cache that deduplicates backtests by normalized parameter key. The cache key is a tuple of (normalized_params, fsm_mode, split_signature). Thread safety is achieved via a threading.Lock combined with per-key threading.Event objects that block concurrent evaluations of the same candidate until the first evaluation completes (lines 503–534). The cache reports hits and misses counters for monitoring.

5.4 Factor Analysis Learning (FSM Model)

Implementation: core/fa_filter.py — functions fit_fa() (line 71) and transform_fa() (line 115).

The Factor Score Model (FSM) augments the deterministic SM by replacing the hand-weighted factor combination with a statistically learned latent-factor decomposition. The learning procedure is as follows:

  1. Feature construction (_build_fa_feature_frame()): The 10 standardized factor columns from compute_signals() are transformed into a feature matrix:
    • Z-score factors (mom_short, mom_long, macd, rsi) are used directly.
    • Volatility is sign-flipped: −vol_z (higher volatility = lower score).
    • Rank factors (bb_position, obv_trend, volume_ratio, price_position, drawdown) are linearly rescaled from [0, 1] to [−1, +1] via (rank − 0.5) × 2; drawdown is additionally sign-flipped.
  2. Standardization: sklearn.preprocessing.StandardScaler is fit only on the training period to avoid look-ahead bias, then applied to both training and test data.
  3. Factor Analysis fitting: sklearn.decomposition.FactorAnalysis(n_components=3, random_state=42) is fit on the scaled training features. The model learns a factor loadings matrix Λ ∈ ℝ10×3 that decomposes the observed 10-dimensional data into 3 latent common factors plus idiosyncratic noise: 
    X = Λ · F + ε,   where F ~ N(0, I),  ε ~ N(0, Ψ)
  4. Sign correction (lines 89–100): Each latent component’s sign is adjusted so that its Pearson correlation with the equal-weight average of the input features is positive. This prevents the arbitrary sign ambiguity inherent in factor analysis from producing a semantically inverted FSM score.
  5. FSM score computation: The sign-corrected latent scores are averaged across the 3 components, then standardized using the training-period mean and standard deviation: 
    fsm_rawt   = mean(Ft,1 × s1,  Ft,2 × s2,  Ft,3 × s3)
fsm_scoret = (fsm_rawt − μtrain) / σtrain
    where sk ∈ {−1, +1} are the sign-correction factors.

The resulting fsm_score replaces the hand-weighted factor score in the SM pipeline. All downstream position sizing, entry/exit counting, and backtest logic remain identical, meaning that the FSM is a strict superset of SM that only differs in how the composite score is constructed.

5.5 ML Signal Filter Training

Implementation: core/ml_filter.py — functions fit_ml_filter() (line 493), build_feature_bundle() (line 339), apply_filter() (line 597).

The ML filter is an optional secondary gate that acts on top of SM/FSM buy signals. It learns to predict, at each buy signal, whether the subsequent trade will generate positive excess return over the buy-and-hold benchmark. Two model architectures are available:

5.5.1 Feature Engineering (29 Features)

Feature extraction is performed by build_feature_bundle(), which samples only at buy-signal positions to avoid data leakage from non-signal days. The 29 features (defined in ML_FEATURE_COLUMNS, lines 37–67) include:

CategoryFeatures
Factor scoresfactor_score, factor_percentile, target_position
Z-score factorsmom_short_z, mom_long_z, macd_z, rsi_z, vol_z
Rank factorsbb_position_rank, obv_trend_rank, volume_ratio_rank, price_position_rank, drawdown_rank

Derivedentry_count (sum of confirming conditions), ema_spread_pct ((ema_fast − ema_slow) / close)

5.5.2 Label Construction

For each buy signal at position t, the label is computed by looking forward horizon days (default 10): 

future_strategy_return = ∏i=1..h(1 + wt+i-1 · rt+i) − 1
future_naive_return    = ∏i=1..h(1 + rt+i) − 1
future_excess_return   = future_strategy_return − future_naive_return
ml_label               = 1{future_excess_return > 0}    (primary: excess return mode)

where wt is the target position weight and rt is the close-to-close return. If the number of valid excess-return samples with both classes is below min_excess_samples (default 20), the label falls back to absolute strategy return: ml_label = 1{future_strategy_return > 0} (absolute return mode).

5.5.3 Logistic Regression

Configuration (lines 548–554): 

StandardScaler  →  LogisticRegression(
    max_iter=1000, solver="liblinear",
    class_weight="balanced", random_state=42
)
  • StandardScaler is fit exclusively on training-period buy signals.
  • class_weight="balanced" automatically upweights the minority class to handle label imbalance (typically more losing trades than winning trades at the margin).
  • L2 regularization (default C=1.0) prevents overfitting to small sample sizes.
  • Output: probability of positive excess return P(label=1|x).

5.5.4 LightGBM Classifier

Configuration (lines 556–571): 

LGBMClassifier(
    objective="binary", n_estimators=200,
    learning_rate=0.05, num_leaves=15,
    min_child_samples=10, subsample=0.9,
    colsample_bytree=0.9, reg_alpha=0.1,
    reg_lambda=0.1, class_weight="balanced",
    random_state=42
)
  • No scaler needed—gradient-boosted trees are invariant to monotonic feature transforms.
  • num_leaves=15 and min_child_samples=10 keep individual trees shallow, serving as an implicit regularizer against small training sets.
  • L1 (reg_alpha=0.1) and L2 (reg_lambda=0.1) leaf regularization further constrain model complexity.
  • subsample=0.9 and colsample_bytree=0.9 add stochasticity to reduce variance.

5.5.5 Degenerate Case Handling

When training samples degenerate to a single class (all labels 0 or all labels 1) or fewer than 8 samples exist, the system does not raise an exception. Instead it returns a _ConstantProbabilityModel (line 126) that outputs the training-set positive rate as a fixed probability for all inputs. This guarantees that the downstream apply_filter() always receives a valid probability vector, maintaining pipeline robustness even under extreme data conditions.

5.6 Adaptive Regime Model Training

Implementation: core/adaptive_regime.py — functions build_adaptive_feature_frame() (line 211), train_adaptive_state_model() (line 341), _fit_state_classifier() (line 296), predict_adaptive_states() (line 387).

The adaptive regime router dynamically selects the best strategy variant conditioned on the current market state. Its training has three distinct phases:

5.6.1 State Feature Engineering (19 Features)

The feature set (ADAPTIVE_STATE_FEATURE_COLUMNS, lines 84–104) captures multi-scale market dynamics:

CategoryFeaturesDescription
Stock returns ret_5, ret_20, ret_60 5-, 20-, 60-day price returns capturing short/medium/long momentum.
Market proxy returns spy_ret_5, spy_ret_20, spy_ret_60 Same look-backs applied to SPY (or market proxy), providing macro context.

5.6.2 Unsupervised State Discovery (MiniBatchKMeans)

Market states are discovered by clustering the 19-dimensional feature vectors into ADAPTIVE_STATE_COUNT = 6 clusters using sklearn.cluster.MiniBatchKMeans: 

MiniBatchKMeans(
    n_clusters=6,
    batch_size=max(64, 6 × 16),
    random_state=42,
    n_init=10
)

The mini-batch variant is chosen for computational efficiency on large feature matrices. The resulting state IDs partition the historical timeline into 6 qualitatively distinct market regimes (e.g., low-volatility uptrend, high-volatility drawdown, range-bound). Cluster centroids and per-state sample counts are stored as artifacts for offline inspection.

5.6.3 Supervised State Classifier

Once states are assigned, a supervised classifier is trained to predict state labels from real-time features (enabling online state classification without re-running KMeans). The classifier selection follows a cascading strategy (_fit_state_classifier(), line 296):

  1. If ≥ 60 samples and LightGBM available: 
    LGBMClassifier(
    objective="multiclass", num_class=6,
    n_estimators=160, learning_rate=0.05,
    min_child_samples=10, subsample=0.9,
    colsample_bytree=0.9, random_state=42
)
  2. Otherwise (fallback): 
    Pipeline([
    StandardScaler(),
    LogisticRegression(
        max_iter=1200,
        multi_class="multinomial",
        random_state=42
    )
])
  3. Degenerate case (≤ 1 unique state): DummyClassifier(strategy="most_frequent") is used to maintain API compatibility without meaningful predictions.

5.6.4 Routing Policy Selection

For each discovered state, the system evaluates all candidate strategy variants (defined in ADAPTIVE_OFFLINE_CANDIDATE_MODEL_IDS, 11 candidates including naive, mean, drift, SM, FSM, and all optimized variants) and selects the one with the best weighted performance metric on that state’s historical days. The per-state best candidate forms the routing policy: a lookup table from state ID to strategy variant. This offline-learned routing policy is stored as routing_policy.csv and routing_policy_summary.json within the regime_artifacts/ directory.

5.7.8 Model & Optimization Selection

Beyond parameter sliders, the webapp sidebar (and the single-stock analysis workflow at ui/single_stock.py and ui/single_stock_workflow.py) provides controls for selecting:

  • Signal Model: SM (Simple Model, hand-weighted factors) or FSM (Factor Score Model, learned factor analysis weights).
  • ML Filter Toggle: Enable/disable the ML signal filter overlay (Logistic Regression or LightGBM) on top of SM/FSM signals.
  • Optimization Method: Bayesian (Optuna TPE), Random Search, or Genetic Algorithm for parameter optimization.
  • Regime Model: Legacy dual-state router or Adaptive Router v1 (with automatic degradation fallback if offline artifacts are missing).

5.7.9 End-to-End Reactivity

Streamlit’s reactive execution model means that any sidebar parameter change triggers a complete re-execution of the analysis pipeline: data → indicators → signals → backtest → evaluation → visualization. The user sees updated equity curves, performance tables, and diagnostic charts within seconds. This tight feedback loop enables hands-on exploration of the relationship between parameter choices and strategy performance—directly fulfilling the course requirement that “important parameters should be adjustable in your webapp.”
