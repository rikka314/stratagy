6. Model Checking

This section addresses Requirement 6 of the AIE1902 course project: “Check the models using the methods mentioned in our lecture notes.” We present ten complementary model-checking methodologies implemented across the codebase, ranging from fundamental out-of-sample testing and walk-forward validation to overfitting detection, parameter validity enforcement, ML diagnostics, adaptive regime validation, trade-level analysis, stationarity handling, and standard financial performance metrics. Every method is traced to its concrete implementation with file paths, function names, and line numbers in the repository source code.

6.1 Out-of-Sample (OOS) Testing

Out-of-sample testing is the most fundamental guard against overfitting. Every model evaluation in the pipeline uses a strict train/test split so that all reported metrics are computed exclusively on data the model has never seen during fitting.

6.1.1 Train/Test Split Mechanism

The split is controlled by the train_ratio parameter (default = 0.70, i.e. 70 % training, 30 % testing). In the offline research framework (model-test/model_test/execution.py), the split index is computed as: 

split_idx = int(len(df_window) * lead_task.window.train_ratio)

This split_idx is passed to every pipeline function—signal generation, backtest simulation, and evaluation—so that the training data boundary is respected throughout the entire pipeline. The same split logic is also applied in model-test/model_test/adaptive_router.py for the adaptive regime pipeline: 

split_idx = int(len(df_window) * window.train_ratio)

6.1.2 Baseline Treatment

Critically, baseline models (Mean model, Drift model) use the same train/test split to avoid look-ahead bias. Baseline forecasts are generated using only data in df[:split_idx], and all comparative metrics are reported on df[split_idx:] (the test set) only.

6.1.3 Metrics Computed on Test Set

All reported metrics are computed via the function compute_performance_metrics() in core/evaluation.py (line 14). This function takes the strategy equity curve and a benchmark equity curve, and returns the following dictionary of metrics:

KeyMetricFormula
cumret Cumulative Return equity[-1] / equity[0] − 1
annret Annualized Return (equity[-1] / equity[0])252/n − 1
maxdd Maximum Drawdown min(equity / cummax(equity) − 1)
sharpe Sharpe Ratio (annualized) (mean(r) − rf/252) / std(r) × √252
bench_cumret Benchmark Cumulative Return Same formula applied to benchmark equity
excess_return Excess Return cumret − bench_cumret

6.2 Walk-Forward Validation

While a single train/test split validates performance on one specific out-of-sample period, walk-forward validation extends this by sliding a rolling window across the entire dataset, producing multiple independent out-of-sample segments. This tests whether the strategy performs consistently across different time periods—not just one particular test set.

6.2.1 Implementation

Location: core/backtest.py, function walk_forward_backtest() (line 241).

Function signature:

def walk_forward_backtest(
    df: pd.DataFrame,
    train_window: int,
    test_window: int,
    stop_loss_mult: float,
    take_profit_mult: float,
) -> tuple[pd.DataFrame, pd.DataFrame]

6.2.2 Algorithm

The walk-forward procedure operates as follows:

  1. Initialization: Set start_idx = 0.
  2. Window Partitioning: For each iteration:
    • Training window: df[start_idx : start_idx + train_window]
    • Test window: df[start_idx + train_window : start_idx + train_window + test_window]
  3. Backtest on Test Segment: Run simulate_strategy() on the test slice with initial_position=0 and the specified stop-loss/take-profit multipliers.
  4. Per-Window Metrics: For each window, record:
    • test_return: total return over the test segment
    • test_sharpe: Sharpe ratio of daily strategy returns in the test segment
    • test_max_drawdown: worst peak-to-trough decline during the test segment
  5. Equity Curve Chaining: Each segment’s equity curve is scaled so it continues from the previous segment’s final equity value: 
    segment["strategy_equity"] *= prev_end
segment["buy_hold_equity"] *= prev_bh_end
    This produces a single, continuous equity curve across all walk-forward windows.
  6. Advance: start_idx += test_window and repeat until the dataset is exhausted.

6.2.3 Interpretation

Walk-forward validation reveals temporal consistency. A model that performs well in a single OOS split but poorly under walk-forward testing likely benefits from a favorable test period rather than genuine predictive power. By examining the distribution of per-window returns and Sharpe ratios, we can detect regime-dependent fragility and assess whether the strategy degrades gracefully across market conditions.

6.3 Rolling Robustness Testing (Offline Research Framework)

The offline research framework in model-test/ implements a systematic, multi-window robustness validation that goes beyond the single-pass walk-forward approach. This is the framework used for large-scale hyperparameter searches and model comparisons.

6.3.1 Configuration

Location: model-test/model_test/models.py (lines 48–50) and model-test/model_test/config.py (lines 105–107).

ParameterDefaultMeaning
rolling_window_days 504 Each rolling window spans ~2 trading years
rolling_step_days 126 Windows are offset by ~6 trading months
rolling_window_count 3 Three overlapping windows are evaluated

6.3.2 Window Construction

Windows are constructed in reverse chronological order from the end of the available data (model-test/model_test/config.py, lines 406–419): 

for ordinal in range(config.rolling_window_count):
    offset = config.rolling_window_count - ordinal - 1
    end_idx = df_len - offset * config.rolling_step_days
    start_idx = end_idx - config.rolling_window_days

With default settings (504-day windows, 126-day step, 3 windows), the three windows overlap substantially, covering approximately the most recent 756 trading days (~3 years) with significant overlap between adjacent windows.

6.3.3 Two-Stage Validation Process

  1. Stage A — Candidate Discovery: A broad search across the parameter space using the primary evaluation window. Top-N candidates are selected based on a composite score.
  2. Stage B — Robustness Retest: The top candidates from Stage A are re-evaluated across all rolling windows. The results are aggregated into robustness_summary.csv (model-test/model_test/runner.py, line 444–452), which is generated by the build_robustness_summary() function.

6.3.4 Robustness Summary Metrics

The robustness_summary.csv file aggregates across all rolling windows for each candidate model:

  • Mean Return: Average cumulative return across all windows
  • Mean Sharpe: Average Sharpe ratio across all windows
  • Return Std Dev: Standard deviation of returns across windows (lower is more robust)
  • Max Drawdown: Worst maximum drawdown observed across any window

A model is considered robust only if it delivers consistent positive performance across all rolling windows. High variance across windows signals parameter fragility or regime dependence.

6.4 Overfitting Detection via Train-Validation Gap Penalty

Overfitting is the most pervasive risk in quantitative strategy development. The optimizer explicitly addresses this through a multi-pronged scoring function that penalizes train/validation divergence.

6.4.1 Composite Score with Gap Penalty

Location: core/optimizer.py (lines 424–426).

The optimizer’s objective function computes a composite score as:

raw_score = 0.25 × train_score
           + 0.75 × validation_score
           − 0.20 × |train_score − validation_score|

This formula has three key properties:

  1. Validation-weighted (75%): The score is dominated by out-of-sample performance, ensuring the optimizer does not chase in-sample fit.
  2. Gap penalty (20%): Models where |train_score − validation_score| is large are penalized. This directly detects overfitting—a model that scores 0.9 on training but only 0.3 on validation (gap = 0.6) receives a penalty of 0.12, which can easily push it below a more consistent model.
  3. Training contribution (25%): A modest weight on training score prevents the optimizer from selecting models that are unstable even on training data.

6.4.2 Regularization Penalty

Location: core/optimizer.py, function _regularization_penalty() (line 229).

An additional regularization term prevents parameters from straying far from sensible defaults, which is an implicit overfitting guard: 

def _regularization_penalty(candidate_params, *, lam=0.02, param_space=None):
    penalty = 0.0
    for name, (default, lo, hi, param_type) in active_param_space.items():
        if param_type == "bool":
            penalty += float(normalized[name] != _coerce_bool(default))
            continue
        span = hi - lo
        if span > 0:
            penalty += ((normalized[name] - default) / span) ** 2
    return lam * penalty

Mathematically, for continuous parameters:

R(θ) = λ × ∑i ((pi − di) / (hi − li))2

where pi is the candidate value, di the default, hi and li the upper and lower bounds, and λ = 0.02. This is analogous to L2 regularization (ridge regression) applied to the strategy’s parameter space. Parameters that deviate significantly from their defaults incur a quadratic cost, biasing the optimizer toward simpler, more conventional parameterizations that are less likely to be overfit.

6.4.3 Final Objective

The optimizer’s final objective across all three optimization methods (Bayesian, Random Search, Genetic Algorithm) is:

final_score = raw_score − _regularization_penalty(θ)

This is applied consistently at lines 735, 824, and 967 of core/optimizer.py, ensuring that regardless of the search algorithm, the same anti-overfitting safeguards are active.

6.5 Parameter Validity Constraints

Location: core/optimizer.py, function _is_valid_candidate() (line 208).

Before any candidate parameter vector is evaluated, it must pass a set of structural validity constraints that prevent degenerate or economically meaningless configurations: 

def _is_valid_candidate(candidate_params, *, param_space=None) -> bool:
    normalized = _normalize_candidate_params(candidate_params, param_space=param_space)
    if normalized["ema_fast"] >= normalized["ema_slow"]:
        return False
    if normalized["macd_fast"] >= normalized["macd_slow"]:
        return False
    if normalized["entry_threshold"] <= normalized["exit_threshold"]:
        return False
    if "momentum_short" in normalized and \
       normalized["momentum_short"] >= normalized["momentum_long"]:
        return False
    if "score_mid_pct" in normalized and \
       normalized["score_mid_pct"] >= normalized["score_high_pct"]:
        return False
    if "exit_min_signals" in normalized and \
       normalized["exit_min_signals"] > normalized["entry_min_signals"]:
        return False
    return True

6.5.1 Constraint Rationale

ConstraintEconomic Rationale
ema_fast < ema_slow A “fast” moving average must respond more quickly than a “slow” one; violating this inverts the crossover signal logic
macd_fast < macd_slow Same logic for MACD’s constituent moving averages; reversal would negate the convergence/divergence interpretation
entry_threshold > exit_threshold The signal strength required to enter a position must exceed the threshold to exit; otherwise the strategy would oscillate between entry and exit on every bar
momentum_short < momentum_long Short-term momentum lookback must be shorter than long-term; reversal conflates the two time horizons
score_mid_pct < score_high_pct The composite score threshold for “mid” conviction must be lower than “high” conviction; inverting would make the scoring tiers incoherent
exit_min_signals ≤ entry_min_signals Exiting a position should require no more confirming signals than entering; otherwise, exit conditions become harder to trigger than entry conditions, creating asymmetric risk

These constraints reduce the search space from an unconstrained Cartesian product of parameter ranges to a convex feasible region, eliminating pathological parameterizations before the expensive backtest simulation is invoked. Invalid candidates are rejected immediately (line 393: if not _is_valid_candidate(normalized, param_space=param_space): ...).

6.6 ML Filter Model Diagnostics

Location: core/ml_filter.py.

When the ML filter (LightGBM-based trade signal classifier) is trained, comprehensive diagnostics are computed to validate model quality.

6.6.1 Classification Metrics

The module imports from sklearn.metrics (line 17):

  • Precision: precision_score(y_true, y_pred) — fraction of predicted positive trades that are actually profitable
  • Recall: recall_score(y_true, y_pred) — fraction of actually profitable trades that the model identifies
  • F1 Score: f1_score(y_true, y_pred) — harmonic mean of precision and recall
  • Average Precision: average_precision_score(y_true, y_score) — area under the precision-recall curve, a threshold-invariant metric

These metrics are computed on both the training set and the validation set, enabling direct comparison to detect overfitting within the ML model itself.

6.6.2 Degenerate Case Detection

Location: core/ml_filter.py, class _ConstantProbabilityModel (line 126).

If the training data contains only a single class (e.g., all trades are losses, or all are wins), the LightGBM classifier cannot learn a meaningful decision boundary. Rather than failing or producing undefined behavior, the system detects this degenerate case (line 546) and falls back to a stable placeholder: 

class _ConstantProbabilityModel:
    """Stable fallback model when training labels collapse to a single class."""
    def __init__(self, positive_probability: float) -> None:
        prob = float(np.clip(positive_probability, 0.0, 1.0))
        self.positive_probability_ = prob
        self.classes_ = np.array([0, 1], dtype=int)

    def predict_proba(self, x) -> np.ndarray:
        n_samples = len(x)
        proba_pos = np.full(n_samples, self.positive_probability_, dtype=float)
        return np.column_stack([1.0 - proba_pos, proba_pos])

This model returns the empirical positive class probability for every sample, effectively passing through the base rate without amplifying noise. The predict_proba() interface matches scikit-learn’s API, so downstream code requires no special handling.

6.6.3 Feature Importance

When LightGBM is the underlying classifier, the trained model’s feature_importances_ attribute reveals which technical indicators most influence the trade-filtering decision. This serves as a sanity check: if importance is concentrated on a single noisy feature, the model may be fitting to noise rather than genuine market signal.

6.7 Adaptive Regime Validation

Location: core/adaptive_regime.py.

The adaptive regime model partitions market conditions into discrete states and routes each state to its best-performing strategy variant. Several safeguards validate this model’s quality.

6.7.1 State Distribution Check

Constant: ADAPTIVE_MIN_STATE_DAYS = 20 (line 42).

The function select_routing_policy() (line 505) enforces a minimum sample requirement per state: 

eligible = metrics_df[
    pd.to_numeric(metrics_df["state_day_count"], errors="coerce")
    >= int(min_state_days)
].copy()

States with fewer than 20 observed trading days are excluded from the routing policy selection. This prevents the regime model from making routing decisions based on statistically insufficient evidence. A state observed for only a handful of days may exhibit extreme (but unreliable) performance metrics.

6.7.2 Classifier Quality

The state classifier uses LogisticRegression trained with StandardScaler preprocessing. Feature scaling ensures that all regime features contribute proportionally, and logistic regression provides calibrated posterior probabilities for each state, enabling confidence-based routing.

6.7.3 Graceful Degradation

If the adaptive regime artifacts are missing, corrupted, or fail validation, the system automatically degrades to the legacy dual_state_router. This is signaled through the pipeline result: 

PipelineRunResult.status = "degraded"

This design ensures that the application never crashes due to a faulty regime model; instead, it transparently falls back to a simpler but proven routing mechanism, and the user is informed of the degradation through the status field.

6.8 Trade-Level Analysis

Aggregate metrics like Sharpe ratio can mask problematic trading behavior (e.g., a few lucky trades dominating an otherwise poor strategy). Trade-level analysis decomposes strategy performance into individual trade statistics.

6.8.1 Trade Extraction

Location: core/backtest.py, function extract_trades() (line 127). 

def extract_trades(
    df: pd.DataFrame,
    position_col: str = "position",
    eps: float = 1e-8,
    initial_position: int = 0,
) -> pd.DataFrame

The function:

  1. Identifies contiguous non-zero position segments (position > ε)
  2. Computes per-trade compound return by accumulating daily strategy_return across the trade’s holding period: 
    trade_equity = (1 + strategy_return[start : exit+1]).cumprod()
trade_return = trade_equity[-1] - 1.0
  3. Includes the exit day in the calculation: on the day position drops to zero, the strategy return is still determined by the previous day’s position, so the exit-day return must be included
  4. Outputs a DataFrame with columns: entry_date, exit_date, hold_days, trade_return, is_win

6.8.2 Trade Statistics

Location: core/evaluation.py, function compute_trade_stats() (line 68).

StatisticFormulaInterpretation
Win Rate wins / n_trades Fraction of profitable trades
Profit/Loss Ratio mean(gains) / mean(|losses|) Average winning trade size relative to average losing trade; values > 1 indicate larger wins than losses
Average Hold Days mean(hold_days) How long positions are held on average; combined with win rate, reveals if the strategy is a “fast scalper” or “slow trend follower”
Turnover Ratio n_trades / n_trading_days Frequency of position changes; high turnover increases transaction cost sensitivity

A strategy with a high Sharpe ratio but extremely low win rate and high P/L ratio is “right-tail dependent”—it relies on rare large wins. Conversely, a high win rate with low P/L ratio is “death by a thousand cuts” vulnerable to occasional large losses. Trade-level analysis exposes these pathologies.

6.9 Stationarity Considerations

Financial time series are notoriously non-stationary: their statistical properties (mean, variance, autocorrelation) change over time. Rather than attempting to make the raw series stationary through differencing (which discards level information), our pipeline uses adaptive normalization techniques that implicitly handle non-stationarity.

6.9.1 Rolling Z-Score Normalization

Location: core/indicators.py, function rolling_zscore() (line 29). 

def rolling_zscore(series: pd.Series, window: int) -> pd.Series:
    mean = series.rolling(window=window, min_periods=window).mean()
    std  = series.rolling(window=window, min_periods=window).std()
    z = (series - mean) / std
    return z.replace([np.inf, -np.inf], np.nan)

The Z-score at time t is defined as: 

zt = (xt − μt,w) / σt,w

where μt,w and σt,w are the rolling mean and standard deviation computed over the most recent w observations. This transforms a non-stationary series into an approximately stationary one by comparing each value only to its recent local distribution, not to the global distribution.

6.9.2 Rolling Rank (Percentile) Normalization

Location: core/indicators.py, function rolling_percentile() (immediately following rolling_zscore()).

Rolling percentile rank provides an additional normalization that is robust against distribution shifts. Unlike Z-score (which assumes approximate normality within the window), percentile rank is purely ordinal and invariant to the shape of the local distribution: 

rankt = Percentile(xt, {xt−w+1, …, xt}) ∈ [0, 1]

6.9.3 Controlling Locality via score_lookback

The score_lookback parameter controls the window size for these normalizations. A shorter lookback (e.g., 20 days) adapts quickly to regime changes but may introduce noise; a longer lookback (e.g., 120 days) is smoother but slower to react. This parameter is part of the search space exposed to the optimizer, allowing the system to find the lookback that best balances responsiveness and stability for each asset.

6.9.4 Volatility-Based Position Discount (Heteroskedasticity)

Financial return volatility clusters: periods of high volatility tend to persist (ARCH/GARCH effects). The backtest engine addresses this heteroskedasticity through a volatility-based position discount: during high-volatility regimes, position sizes are reduced. This is economically equivalent to targeting a constant-volatility exposure, a standard technique in professional quantitative finance for handling time-varying risk.

6.10 Performance Metrics (Course Lecture Alignment)

All evaluation metrics align with the standard financial performance measures taught in the AIE1902 course lectures. The implementations are centralized in core/evaluation.py, function compute_performance_metrics() (line 14), with helper functions for the underlying calculations.

6.10.1 Sharpe Ratio

The Sharpe Ratio is the primary risk-adjusted return measure. It quantifies excess return per unit of risk (standard deviation): 

SR = (E[r] − rf / 252) / σ(r) × √252

where r denotes daily strategy returns, rf is the annualized risk-free rate (default 0), and the √252 factor annualizes the daily ratio. A Sharpe ratio above 1.0 is generally considered acceptable; above 2.0 is strong.

6.10.2 Maximum Drawdown

The maximum drawdown measures the worst peak-to-trough decline in the equity curve: 

MDD = mint (equityt / maxs≤t(equitys) − 1)

This metric captures tail risk—the worst historical loss a strategy holder would have experienced. It is reported as a negative number (e.g., −0.25 means a 25% peak-to-trough decline). Maximum drawdown is particularly important because it reflects the psychological and financial pressure an investor faces during the worst period of the strategy.

6.10.3 Cumulative Return

CumRet = equityT / equity0 − 1

The total percentage gain (or loss) over the entire evaluation period. This is the most intuitive measure of strategy performance but does not account for risk or the time period over which the return was generated.

6.10.4 Annualized Return

AnnRet = (equityT / equity0)252/n − 1

Scales the cumulative return to a common annual basis using the 252–trading-day convention. This enables fair comparison between evaluation periods of different lengths. The exponent 252/n assumes compound growth, which is appropriate for equity curve analysis.

6.10.5 Excess Return

ExRet = CumRetstrategy − CumRetbenchmark

The difference between the strategy’s cumulative return and the buy-and-hold benchmark’s cumulative return. Positive excess return indicates the strategy adds value beyond simply holding the underlying asset. This is the most direct measure of whether the active strategy justifies its complexity.
